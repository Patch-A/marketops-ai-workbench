# M0-03 排期与关键路径技术验证

状态：`Completed with documented limitations`

验证日期：2026-08-08

## 1. 验证问题

本验证回答一个有限的工程问题：MarketOps 能否在不依赖大模型的情况下，根据任务工期、完成到开始依赖、显式缓冲、工作日历、锁定日期和硬截止日期，稳定重算活动项目排期，并把冲突暴露给用户。

它不证明生成的任务拆解符合真实客户项目，也不证明工具已经产生商业价值。任务完整性和用户付费仍需真实项目验证。

## 2. 输入边界

`schedule-baseline.csv` 是不可改写的来源基线。`schedule-scenarios.json` 单独保存以下用户确认输入：

- 项目开始日期；
- 周一至周五工作制和显式节假日；
- 明确批准的任务间缓冲；
- 场景中的工期变更。

基准日期之间存在空档，并不自动等于缓冲。当前 2、7、3 个工作日缓冲是合成验证场景的显式输入，不是从真实客户行为推断出的行业规则。

## 4. 计算语义

- 工期按含首尾的工作日计算。
- 依赖仅支持完成到开始关系。
- 缓冲表示前置任务完成与后置任务开始之间的完整工作日数。
- 多个前置任务取最晚完成者作为最早开始约束。
- 锁定日期不自动移动。依赖晚于锁定开始日时返回冲突。
- 总浮时通过反向计算得到，并受项目完工时间和任务硬截止日期约束。零或负浮时任务被标记为关键任务；负值表示当前约束已经无法满足。
- 关键链只连接实际日期上连续驱动的关键任务，因此固定日期可能形成一个独立的关键链入口。

## 5. 暂不支持

- 负责人容量、多人资源平衡、并行投入比例和加班；
- 开始到开始、完成到完成、提前量及部分完成依赖；
- 中国法定节假日自动更新，当前必须显式输入；
- 时区、小时级排期、跨日班次和场地开放时段；
- 概率工期、蒙特卡洛风险模拟和成本优化；
- 自动把来源日期空档解释为缓冲；
- 自动修改锁定日期、正式方案或已批准排期。

因此这仍是确定性技术原型，不是可直接用于生产项目的完整排期系统。

## 6. M1 采用边界

M1 可以复用本验证的日期语义、依赖校验、锁定冲突和结果哈希约束。进入产品实现前仍需增加版本化变更、人工审批、撤销、审计记录、错误恢复和可编辑界面。

如果真实项目需要资源平衡或复杂依赖，应在 M0-05 比较成熟调度组件，而不是继续扩大本脚本。只有候选组件能保留确定性结果、Apache-2.0 项目边界和可解释冲突时才可采用。

