## 3. Frozen HTTP Contract

- `POST /v1/projects/{projectId}/wbs-plans` creates or replays a plan from `reviewRunId` and `reviewVersion`.
- `GET /v1/projects/{projectId}/wbs-plans/{planId}` reads the latest plan or an explicit positive `planVersion`.
- `POST /v1/projects/{projectId}/wbs-plans/{planId}/revisions` creates one append-only revision from `expectedPlanVersion` and non-empty task updates.
- `POST /v1/projects/{projectId}/wbs-plans/{planId}/schedule-snapshots` creates or replays a deterministic schedule from `expectedPlanVersion`, `projectStart`, and explicit ISO holiday dates.

Authentication scope is resolved only by the existing server authenticator. Organization, workspace, client, actor, proposal identity, review content, plan digest, schedule digest, timestamps, and identifiers are never accepted as client-owned facts.

Create-plan replay is keyed by the persisted review run and review version. Schedule replay is keyed by the persisted plan version and deterministic schedule digest. Revisions intentionally use optimistic concurrency: an uncertain retry after a successful commit returns `PLAN_CONFLICT` and requires a fresh read, rather than risking a duplicate append.

All successful and failure responses use `Cache-Control: no-store`. Failure bodies expose stable codes and public messages only.

## 4. Request Limits And Failure Mapping

- JSON content type is required for all writes.
- Duplicate object keys, unknown fields, non-canonical path UUIDs, non-canonical positive integers, empty update arrays, duplicate task updates, duplicate holidays, and request bodies over 128 KiB fail closed.
- Stable mappings include `400` malformed input, `403` invalid server scope, `404` missing review/plan, `409` source or plan conflict, `413` oversized JSON, `422` incomplete review or invalid WBS/schedule domain input, `500` invalid server allocation, and `503` repository failure.
- Cancellation propagates and unexpected exceptions are sanitized.
