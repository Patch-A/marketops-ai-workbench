## Decision Boundary

Confirmed engineering evidence establishes that a project can explicitly cite a
same-client approved rendering and that revocation/revision fail closed. It does
not establish that historical knowledge improves a user's planning outcome,
reduces errors, or is wanted for a later project.

M2-04 therefore has two separate evidence tracks:

1. Engineering isolation: rerun the approved/unapproved paired authorization
   experiment and negative tenant tests against current code. This can use
   synthetic fixtures.
2. Usefulness evaluation: compare a no-history and approved-history planning
   pass on one authorized, de-identified task with an identified human evaluator
   and predeclared criteria. Synthetic examples can exercise the protocol but
   cannot close this track.

- Owned paths: this plan, M2-04 evaluation protocol/fixtures/tests, and the

## Evaluation Protocol

The evaluator receives the same de-identified planning brief twice. In the
control condition, no historical knowledge is available. In the treatment
condition, the only extra input is a visible citation containing the approved
rendering, source-project identifier, effective scope, and citation reason.

Pre-register before running:

- one planning task and anonymization/authorization record;
- one evaluator and the review rubric for factual errors, unsupported claims,
  useful retained controls, and whether a citation was actually adopted;
- a stop condition: any serious factual, privacy, or cross-client leakage ends
  the evaluation and leaves M2-04 incomplete.

The record must distinguish observed results from evaluator opinion. It must not
claim demand, ROI, time savings, repeat use, or payment from one paired run.

## Reproducible Engineering Evidence

`scripts/run_m2_04_isolation_gate.py` reruns the current real PostgreSQL
M2-03 authorization suite. It covers explicit same-client elevation; citation
read fail-closed after revoke or revision; direct-SQL actor, target-project,
client, and workspace rejection; audit rollback; replay; and cite/revoke
concurrency. Its JSON output is labelled synthetic engineering isolation and
explicitly cannot satisfy the usefulness track.

Confirmed on 2026-08-17: the dedicated gate passed against a newly provisioned,
temporary PostgreSQL 18.4 container after the existing M2-02 test container
correctly rejected the current migration chain as drifted. The runtime suite
now also asserts that a project-only approval cannot cite into a same-client
sibling project before explicit client elevation. The temporary container was
removed after the run.

`validation/templates/m2-04-paired-evaluation-record.json` is a metadata-only
template. It records a reference and digest for an authorized de-identified
brief, not the brief itself; a pseudonymous evaluator reference; pre-registered
criteria; non-blind condition order; the same brief digest in both conditions;
the no-history / approved-citation-only conditions; the rubric; and limitations.
`scripts/check_m2_04_evaluation_record.py` rejects a completed record that is
synthetic or lacks authorization, an independent evaluator, an evaluation date,
or pre-registration. Completed records additionally require real SHA-256
digests for the brief, both outputs, the approved rendering, and evaluator
notes/opinion; external references for the task, outputs, citation snapshot,
and notes; a positive citation promotion version with an explicit project or
client scope; complete per-condition measures; and a failed/stopped outcome
when a serious factual or privacy issue is observed. The stricter checks keep
the repository metadata-only and prevent placeholder records from being
mistaken for usefulness evidence.

The current contract deliberately permits no descriptive reference, note,
opinion, claim, limitation, or control label in a record. Every committed
string is either a fixed code, a SHA-256 digest, a timezone-aware timestamp,
or a type-prefixed opaque hexadecimal reference. A completed passing record
must use client-scoped treatment knowledge, bind citation target/workspace/client
metadata to the task (including source and target client/workspace), differ from its source project, record no serious,
privacy, or cross-client issue, keep `preRegistration < evaluation <= completion`,
and show actual treatment citation adoption plus an adopted treatment control.
These checks limit accidental disclosure and invalid completion claims; hashes
and opaque references still cannot prove external authorization,
de-identification, or evaluator independence.
