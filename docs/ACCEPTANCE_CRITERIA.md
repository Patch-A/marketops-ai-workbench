# 验收标准

本文件中的阈值是产品验收目标，不是行业事实。市场 Go/No-Go 仍需真实项目行为和付费验证。

## 1. P0 功能验收

| 编号 | 场景 | 验收结果 |
|---|---|---|
| F-01 | 导入已确认方案 | 原件保存，解析结果可查看，失败可重试 |
| F-02 | 提取交付物 | 每项可接受、修改、驳回，并记录来源和原因 |
| F-03 | 生成排期 | 生成任务、工期、负责人占位、依赖和日期 |
| F-04 | 修改关键日期 | 所有受影响任务重新计算，人工锁定日期不被覆盖 |
| F-05 | 执行更新 | 支持未开始、进行中、阻塞、完成和取消，并保存实际时间 |
| F-06 | 市场变化 | 显示来源、时间、可信度和受影响对象，不自动改正式计划 |
| F-07 | 周报 | 只使用当前项目真实状态，未确认内容明确标记 |
| F-08 | 项目归档 | 生成 Project Capsule，原件、终稿、计划、实际和复盘可追溯 |
| F-09 | 候选知识 | 未经用户确认不能跨项目生效 |
| F-10 | 新项目复用 | 显示引用了哪条知识、来源项目和适用范围 |

## 2. 数据与安全验收

- 项目 A 的原始资料无法被无权限的项目 B 检索。
- 删除源文件后，解析文本、向量、缓存和派生引用按策略处理。
- 模型密钥不出现在浏览器源代码、日志、导出文件和 Git 历史中。
- 外部模型调用可按项目关闭，并显示将发送的数据范围。
- 正式方案修改、知识提升、外部发送和权限变更写入审计日志。
- 所有连接器可单独撤销，撤销后不继续后台同步。

## 3. AI 质量验收

- 结构化输出必须通过 Schema 校验；失败不写入正式项目状态。
- 可核实事实必须带来源，找不到来源时标为未知或假设。
- 日期和依赖由确定性引擎计算，模型不能直接写入未校验日期。
- 同一测试样本重复运行时，关键必需任务不得随机缺失。
- AI 失败、超时或额度不足时，用户可以继续手工完成项目。

## 4. 知识与学习验收

- 候选知识包含来源、证据、范围、状态和确认人。
- 用户可以批准、修改、停用、删除和查看历史版本。
- 项目 A 的知识用于项目 B 时必须显示引用理由。
- 至少完成一次“无历史知识”和“使用批准知识”的配对测试。
- 使用历史知识后不能增加严重事实错误或跨客户泄漏。
- 系统记录被采用、驳回和撤销的知识，而不是只记录生成数量。

## 5. 可用性与可访问性验收

- 主要流程在 375px、768px、1024px 和 1440px 宽度无内容遮挡。
- 核心操作可用键盘完成，焦点可见。
- 空、加载、部分成功、错误、驳回、修订和取消状态有明确反馈。
- AI 建议、来源事实、人工修改和已批准内容视觉上可区分。
- 长任务显示进度、当前步骤、停止、重试和成本信息（若可得）。

## 6. 部署与运维验收

- 新环境可按 README 使用 Docker Compose 启动。
- 提供健康检查、数据库迁移、备份和恢复步骤。
- 服务重启后项目状态和已排队任务不会静默丢失。
- 公开仓库不包含研究 PDF、真实客户资料、密钥或未审计第三方副本。
- 依赖清单记录许可证和采用理由。

## 7. 业务 Go 条件

技术验收可以使用公开案例重构和合成样本；业务 Go 必须至少完成三个实时任务运行，覆盖至少两名目标用户，其中至少一次是同一用户的第二次使用：

- 方案到首版排期的人工时间中位数减少至少 30%。
- 严重事实、品牌、法律或隐私错误为 0。
- 关键任务和依赖的专业盲评不低于人工基线。
- 至少 70% 的生成任务被直接保留或小改后保留。
- 至少两名目标用户主动要求在下一个真实项目复用。
- 至少一名用户愿意为第二个项目、部署或实施服务付款/付订金。

若核心价值用一张表格和简单 Skill 即可达到相近质量、稳定性和维护成本，应停止独立产品开发或转为服务/模板。
